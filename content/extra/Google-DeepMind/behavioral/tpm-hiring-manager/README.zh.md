# 技术项目经理（TPM）用人经理面：技术深度与干系人管理

## 题目

Google DeepMind 的技术项目经理（Technical Program Manager，TPM）流程，目前只有一句话的记录：招聘初筛之后是一轮用人经理面，考技术深度和干系人管理（stakeholder management）。具体问了什么，没有人写下来。下面两组题是按这句描述补写的，场景都放在“TPM 和机器学习研究团队、工程团队一起做事”里。这一轮多长也没有记录，练习时按 45 分钟、每题口头回答 2–3 分钟来练。

### 技术深度

- 挑一个你做过项目管理的机器学习系统（训练流水线、评测平台、模型服务都可以）。在白板上画出它的结构：数据从哪里来，经过哪几步，结果交给谁。然后指出其中真正的技术风险在哪一处，并说明你当时凭什么知道是那里。
- 一次多团队的模型发布，发布条件里有一道评测关卡（evaluation gate）：新模型必须在一组评测上超过旧版本才能发布。这道关卡已经连续三次没过，每次团队都说“再给两周”。你今天接手这个项目。头两周你做什么？你怎么分辨这是模型的问题、评测的问题，还是计划的问题？
- 研究团队告诉你：“这个实验还要三到六周，要看结果。”而产品方的发布日期是固定的。讲一次你把这种说不准的研究工作排进固定日期计划的经历：你怎么排的，留了什么余地，事先定了哪些“到时候就改方案”的条件。
- 你不是系统的作者。讲一次你发现工程师或研究员给你的说法站不住的经历——估计过于乐观、漏了一个依赖，或者指标的算法和大家以为的不一样。你是凭什么起疑的，怎么核实的，又是怎么提出来的？
- 一个大模型训练到一半，有人发现训练数据里混进了一部分评测集的内容（数据污染，contamination）。这时离计划的发布日期还有四周。请说出你会怎么组织这件事的技术评估：要回答哪几个问题，各由谁来回答，哪些决定不该由你来做。
- 模型上线前，推理成本超出了预算。工程团队提了三条路：量化（quantization）、蒸馏（distillation）成一个小模型、限制输出长度。选哪一条不由你定，但你要把它排进计划。每条路你至少要弄懂什么，才能估出它对日期、算力和评测关卡的影响？你会问工程团队哪几个问题？

### 干系人管理

- 研究团队要用一批加速器（GPU 或 TPU）跑一组大实验，产品团队要用同一批机器做发布前的评测和微调（fine-tuning）。两边都说自己更急，而你没有分配算力的权力。你怎么推动出一个决定？
- 一位研究员认为模型已经可以发布；一位工程负责人认为还不行，他担心的是服务稳定性，以及出问题时能不能回滚（rollback）。两人的职级都比你高。你怎么处理这次分歧？
- 你确认项目要晚三周，而你的上级上周刚向更高层汇报过“按计划进行”。你什么时候说、先对谁说、怎么说？请直接说出你那条消息的前三句话。
- 一位总监（director）要求在已经定好的范围里再加一项功能，日期不变。你判断做不到。讲一次你对职级比你高很多的人说“不”的经历；如果没有这样的经历，就说这一次你会怎么说。
- 评测团队同时支持五个项目，你的项目排在第四。你需要他们在两周内加一组新的评测。你对他们没有管理权，这件事也不在他们这个季度的目标里。你怎么办？
- 负责发布前安全评审（safety review）的同事提出了一个问题，认真处理就要推迟发布。产品负责人觉得这是小题大做，希望你“想办法让它过”。你怎么做？

### 技术深度

**在考察什么。** 用人经理不指望 TPM 写代码，也不指望 TPM 替研究员做判断。他想知道四件事：

1. 你能不能把系统讲到“幻灯片下面一层”：数据怎么流，哪一步慢，哪一步容易坏，哪一块归哪个团队。
2. 你能不能指出风险真正在哪里，并且说得出依据，而不是把所有风险念一遍。
3. 你能不能把技术上的不确定变成计划里的东西：余量、检查点、备选方案、事先约定好的决策条件。
4. 你清不清楚自己懂到哪里为止。到了边界，你会不会说“这一点我不知道，我会去问某某”。

**回答骨架（约 2 分钟）。**

1. 一句话：系统做什么、给谁用、大致多大（只说你确实知道的量级）。
2. 三到五个方框：输入 → 处理 → 输出，并标出团队之间的交接处。
3. 风险在哪一处，依据是什么。常见的依据有四种：以前在这里延过期；这里没有回退方案；这里要等别的团队；这里的度量本身不稳定。
4. 你做了什么，让风险变小，或者更早暴露。
5. 结果，再加一句“现在我会改的一点”。

**逐题提示。**

- **画结构、指风险。** 按上面的骨架说。追问通常是“为什么不是另外那一处？”，所以要准备好比较：另一处为什么没那么危险。
- **评测关卡三次没过。** 先别催。把三次的记录摆出来：每次改了什么，离门槛差多少。再问一个问题：“同一个模型重复评两次，分数会差多少？”如果波动比离门槛的差距还大，问题在评测；如果每次都稳定地差一截，问题在模型；如果每次同时改了好几样，没人说得清哪样有用，问题在计划。然后弄清谁有权改门槛（不是你），和各方约定一个决策日期，以及到那天可以选的方案：缩小范围发布、推迟、停止。最扣分的两种回答是“我会推动团队尽快通过”和“我会建议把门槛调低”。
- **把研究估计排进固定日期。** 把“研究里程碑”（弄清了一件事）和“交付里程碑”（做成了一件事）分开记。关键路径上的工作按估计里悲观的那一头排。给实验设时间盒（time-box）和事先写好的判断条件，例如“到第四周指标还没到某个值，就改用已知可行的旧方案”。同时让备选方案低成本地往前走。向上汇报时给区间和把握程度，不只给一个日期。
- **发现说法站不住。** 起疑的理由要具体：同类任务过去三次实际花了多久；依赖清单里少了谁；指标的分子分母是什么、用的是哪一份数据。核实的办法：请对方带你走一遍；请第二个人看；做一个小检查。提出来的方式：先私下说，带着数据，用提问而不是指责。
- **数据污染。** 要回答的问题有三类。范围：哪些数据、占多少、影响到哪些检查点（checkpoint）。影响：评测结果还能不能信——在被污染的评测上得的分数，不能拿来过关卡。补救：从干净的检查点重新训练、过滤数据后继续训练、换一套新的评测集，各要多少算力和几周。谁来回答：范围由数据和训练的负责人查；评测还有没有效，由评测负责人和研究负责人判断；日期怎么取舍，由产品负责人和这个项目的决策人定。你的事是：几天之内把事实查清，把方案和代价写在一页纸上，确保有人做了决定，并且记录下来。不该由你做的是：判断“混进去这么一点没关系”。
- **三条降成本的路。** 你不用会做，但要知道每条路动了什么。对每条路问同样四个问题：模型的输出会不会变（会变，就要重新过评测关卡）；要不要重新训练（要，就得按周算，还要算力）；做完之后能不能退回去；由谁验收。一般的情况是这样：量化是降低权重的数值精度，常见的做法（训练后量化）不用重新训练，工期短，但质量可能下降，要重新评测。蒸馏是训练一个小模型去模仿大模型，要一次新的训练和一轮完整的评测，工期最长。限制输出长度几乎不动模型，但改了产品行为，要产品负责人同意。具体到这个模型是不是这样，以工程团队的回答为准。然后把三条路的工期、算力、要不要重评、能不能退回列成一张表，交给有权选的人。失分的回答有两种：自己直接选一条；只问“要几周”，不问评测要不要重做。

**最常见的失分方式。**

- 只讲流程（“我每周开同步会，维护一张风险表”），讲不出系统的任何一个具体细节。
- 名词很多，往下追问一层就答不上来；不知道的地方硬编。直接说“这一层我不清楚，当时由某某负责，我的做法是……”反而加分。
- 风险列了一长串，不排序，也说不出哪一个真的发生过。
- 延期全是别人的原因。
- 替专家做技术决定；或者反过来，把自己说成只负责传话和写会议纪要。
- 讲前雇主的保密细节。说量级和结构就够了，不要报内部代号和没有公开的数字。

**示例回答（第一题，约 90 秒；内容是编的）。**

> “我管过一个文生视频（text-to-video）模型的发布项目，涉及三个团队：训练、评测、推理服务。结构是这样的：训练团队每两周交一个候选检查点；评测团队对它做两类评测，一类是自动指标，一类是人工两两对比；过了门槛，服务团队再做加速和部署。
>
> 表面上最大的风险是训练，因为它最贵。但我翻了前两个版本的记录，两次延期都出在人工评测上：一轮要五个工作日；而且同一个模型重复评两次，胜率能差三个百分点，门槛却只要求比上一版高两个点。也就是说，评测的波动比要测的差距还大，过不过关有一部分是运气。
>
> 我做了三件事。第一，请评测负责人加大每一轮的样本量，并且报告置信区间，而不只是一个数。第二，把人工评测从最后一步改成每个候选都先跑一个小样本版，问题能早两周暴露。第三，和三位负责人事先约定：到第六周，如果区间还跨着门槛，就按缩小范围的方案发布。
>
> 最后我们比原计划晚了一周，但没有再出现临发布才发现不过关的情况。回头看，我应该在项目启动时就问‘这个评测重复跑一次会差多少’，而不是等到第二次延期。”

这个回答得分的地方：指出的风险和直觉不一样，并且有记录作依据；做的三件事都对着这个风险；没有替评测团队决定样本量该是多少；最后有一句诚实的复盘。

### 干系人管理

**在考察什么。**

1. 决定权不在你手里时，你能不能让决定被做出来：谁来定，按什么标准，什么时候定。
2. 坏消息你是不是说得早，而且带着方案。
3. 面对职级高的人，你能不能用事实和备选方案表示不同意；对方做了决定之后，你能不能照做。
4. 你转述各方立场是不是公道。研究员和工程负责人听了你的描述，都应该会说“对，我就是这个意思”。
5. 你会不会让人意外：不背着当事人往上报（escalation），不当面答应、背后不做。

**回答骨架。** 假设题按这五步说：

1. 先弄清事实，以及每一方真正要的是什么：要什么，哪天要，拿不到的代价是什么。
2. 找出谁有权决定、按什么标准。如果没有现成的标准，先推动把标准定下来。
3. 把选项写出来，每个选项的代价用同一种单位表示（几周、多少算力、多大风险）。
4. 先让当事双方直接谈。谈不拢，再带着双方都认可的事实描述，一起往上报。
5. 决定之后：记录、通知、跟进。事后要改的是规则，不是追究某个人。

经历题按这个顺序说：情境（两句）→ 我当时的判断 → 我做了什么 → 结果（尽量有数字）→ 之后我改了哪个做法。

**逐题提示。**

- **算力冲突。** 不要一上来就“各分一半”。先查事实：两边各自的截止日期，晚一周的代价，任务能不能拆开或者错开时间跑。再问清这里的算力由谁分配、组织当前的优先级是什么。然后提一个具体的排期方案，请双方来改。谈不拢，就写一页纸，两位负责人一起去找有分配权的人。事后提议一条常设规则，下次遇到同样的冲突不用再往上报。
- **研究员和工程负责人意见不同。** 他们回答的其实是两个问题：“模型够不够好”和“出了事我们接不接得住”。把发布条件逐条写出来，分别问两位：“看到什么证据，你会改主意？”再找中间方案，例如先小范围发布，回滚先演练一遍。最后由有权决定发布的人来定，你不投票。
- **向上报告延期。** 确认延期属实的当天就说，不等想出解决办法。先告诉直接上级：他上周刚报过“按计划进行”，不能让他从别人那里听到。消息里依次是：什么变了；新日期和把握程度；一句话原因；方案，以及你需要他做的决定。
- **对总监说“不”。** 不说光秃秃的“不行”。说清楚范围、日期、质量、人手这四样不能同时不变，给出两三个方案和各自的代价，推荐其中一个，请对方选。如果对方仍然决定硬加，就照做，同时把风险写下来，约好检查点。
- **请评测团队帮忙。** 先了解排在你前面的三个项目是什么，为什么排在前面。把请求缩到最小；能自己做的准备（数据、规格说明）先做好；想一想你能给对方什么，例如出一个人帮忙，或者把新评测做成别的项目也能用的。和对方的负责人公开谈取舍，不绕过他。实在排不进去，就和他一起去找同时管这两个优先级的人。
- **安全评审提出问题。** 评审不是要绕开的障碍，TPM 也没有权力免掉它。先把担忧说具体：会出什么事，可能性多大，后果多重，什么证据能打消它。把产品负责人和评审的同事请到一起谈，找在原定日期内能做完的缓解措施。如果确实要推迟，就按“向上报告延期”那一题的办法尽早说。“我会想办法让它过”是这一题最扣分的回答。

**最常见的失分方式。**

- 把自己讲成裁判（“最后我决定……”），或者讲成信使（“我把问题报给了老板”）。TPM 的贡献在两者之间：让该做决定的人，拿着清楚的选项做了决定。
- 只有过程，没有结果；或者结果只有一句“大家都很满意”。
- 说其他团队或前同事的坏话。
- 坏消息拖到有了解决办法才说。
- 对上级说“不”，却没有备选方案；或者当面答应，事后不做。
- 在假设题里编造这家公司的内部流程。

**示例回答（第三题，约 90 秒；内容是编的）。**

> “我会在确认延期属实的当天说，先告诉我的直接上级。他上周刚向上报过‘按计划进行’，不能让他从别处听到。
>
> 消息的前三句是：‘视频模型的发布日期要从 3 月 10 日推到 3 月 31 日左右，我有八成把握不会更晚。原因是评测关卡第三次没过，定位问题加重新评测需要三周。我准备了两个方案，想今天下午和你过一遍：一是按新日期完整发布，二是 3 月 10 日先发布不依赖新模型的那一部分。’
>
> 然后我会附上一页说明：三次评测的结果，新日期是怎么估出来的，还有哪两件事可能让它再晚。消息里不写是谁的责任。
>
> 我以前有一次等了四天，想先把方案想清楚再报。结果上级在另一个会上先听到了，非常被动。从那以后我的做法是：当天先发三句话，方案第二天补上。”

这个回答得分的地方：先说给谁、为什么是他；前三句里有新日期、把握程度、原因，以及要对方做的事；主动讲了自己做错过的一次，和之后改了什么。

### 值得向用人经理提的问题

- 这个岗位主要支持研究项目、产品发布，还是两者之间的交接？
- 一个模型“可以发布”是谁决定的？TPM 在这个决定里做什么？
- 团队之间争算力或评测资源时，现在是怎么解决的？
- 这个岗位上做得最好的人和做得一般的人，差别在哪里？
- 入职头三个月，你最希望我做成的一件事是什么？

这些问题同时也在补这一页的空白：前面几道假设题里“我会先问清楚”的内容，正好在这里问。
